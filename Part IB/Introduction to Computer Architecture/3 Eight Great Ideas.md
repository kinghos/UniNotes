- Design for Moore's Law
	- Design with the assumption that every new generation would improve performance
- Use abstraction to simplify design
	- High-level languages
	- Assembly language
	- Hardware representation
- Make the common case fast
	- Amdahl's Law:
	$$\text{execution time after improvement}=\frac{\text{execution time affected by improvement}}{\text{amount of improvement}}+\text{execution time unaffected}$$
	- e.g. if integer division is used rarely, a large increase in performance barely affects overall performance
- Performance via parallelism
	- Instruction level parallelism - multiple instructions executed in one clock cycle
	- Thread-level parallelism
	- Data-level parallelism - an instruction can act on more than one data item
- Performance via pipelining
	- Key idea: a production line for executing instructions
	- Break execution into steps e.g. fetch, decode, execute, memory access
- Performance via prediction
	- Predict what might happen next to make the pipeline and memory subsystem more efficient
	- Control-flow prediction
		- Predict what will be executed next, e.g. outcome of conditional branch
	- Data-value prediction - predicting if a value will not change
	- Data-access pattern prediction
		- Ensure that data needed soon is nearby for low-latency access
- Hierarchy of memories
	- Accessing external DRAM is slow (300+ clock cycles)
- Dependability via redundancy
	- Error correcting codes
	- Bit error detection and correction
	- RAID
	- Sizing of transistors - bigger transistors for arithmetic, smallest for memory

#### Definitions of performance
- Performance = 1/execution time
- Relative performance - how much faster one system is to another.
- Execution time measured as total response time, including all aspects
- CPU time: comprises user CPU time and system CPU time
	- CPU clock cycles * clock period
	- Clock cycles = instruction count * cycles per instruction
	- CPU time = instruction count * CPI * clock cycle time
- Instruction count and CPI are dictated by ISA
